# Reference-metabolome behavior — findings

Evidence generated by `src/metaboanalyst/investigate/reference-metabolome-check.R`
(rerunnable from repo root; see that script for the exact commands and full
console output this file summarizes). MetaboAnalystR 4.3.0, run locally
(`.on.public.web == FALSE`) via Rscript.

## Loader signatures

- `Setup.KEGGReferenceMetabolome(mSetObj = NA, filePath)` — `filePath` is a
  **file path**, read line-by-line via `scan(inFile, "character", sep = "\n")`,
  **not** a character vector. It matches each line against
  `cmpd.db$kegg_id` (case-insensitive) and stores the matched subset into
  `mSetObj$dataSet$metabo.filter.kegg`. It does not touch
  `use.metabo.filter`, the pathway library, or the mset library, so it can be
  called any time before the `Calculate*Score()` step that consumes it.
- `Setup.HMDBReferenceMetabolome(mSetObj = NA, filePath)` — same shape, but
  matches against `cmpd.db$name` (compound *names*, despite the "HMDB" in the
  function name — it is a name-matching loader, not an HMDB-ID loader) and
  stores the matched subset into `mSetObj$dataSet$metabo.filter.hmdb`.
- Both loaders branch on a **bare global** `anal.type` (`anal.type %in%
  c("msetora","msetssp","msetqea")`, set by `InitDataObjects()` via
  `anal.type <<- anal.type`) to decide whether to look up compounds in
  `master_compound_db.qs` vs `compound_db.qs`. This means the loader call
  must come **after** `InitDataObjects()`, but its position relative to
  `SetMetabolomeFilter()` / `SetCurrentMsetLib()` / `SetSMPDB.PathLib()`
  does not matter — the filter and the reference vector are both just
  attributes on `mSetObj` that are only *read* inside `CalculateOraScore()` /
  `CalculateHyperScore()`.
- `SetMetabolomeFilter(mSetObj = NA, TorF)` just sets
  `mSetObj$dataSet$use.metabo.filter <- TorF`; it has no independent effect
  without the corresponding `metabo.filter.kegg`/`metabo.filter.hmdb` also
  being populated.

## Pathway module (pathora) — golden Elicit·Up·1mo, Nicotinate & Nicotinamide raw p

- filter OFF: **1.2011e-05** (exact match to Trenton's downloaded value)
- filter ON (primary KEGG reference via `Setup.KEGGReferenceMetabolome`):
  **ERRORS** — `Cannot perform enrichment analysis on a single metabolite
  set!` (surfaces as `object 'current.msg' not found` because `AddErrMsg()`
  itself is also broken locally — see "Package bugs found" below).
- Matches Trenton's downloaded 1.2011e-05: **filter OFF only**.

**Root cause of the filter-ON failure (not just a numeric difference — a
real incompatibility):** `CalculateOraScore()`'s local-execution filter
branch always does
`current.mset <- lapply(current.kegglib$mset.list, function(x) x[x %in%
mSetObj$dataSet$metabo.filter.kegg])`, i.e. it **always** filters against the
KEGG-ID reference vector, regardless of whether the loaded pathway library is
KEGG or SMPDB. We use `SetSMPDB.PathLib()` (required to reproduce the golden
numbers — Task 2). Inspecting the loaded library confirms `current.kegglib$
mset.list` members for SMPDB are **HMDB IDs** (e.g. `HMDB0002134`), not KEGG
IDs (e.g. `C02477`). A KEGG-ID reference vector can never match an HMDB-ID
member list — confirmed by direct check: zero overlap between any SMPDB
library member ID and any of the 35 KEGG reference IDs. So
`SetMetabolomeFilter(TRUE)` + `Setup.KEGGReferenceMetabolome()` on an
SMPDB-library pathway analysis collapses nearly every pathway set to zero
retained members, tripping the package's "too few sets" error path. This is a
genuine package limitation for local/offline SMPDB pathway runs, not a
cosmetic quirk — it independently corroborates that filter-OFF is the only
usable/correct mode for our pathway module, consistent with Trenton's
downloaded Rhistory.R showing filter OFF.

## ORA module (msetora) — same 7 compounds, top pathway + raw p

- filter OFF (no reference): **Nicotinate and Nicotinamide Metabolism**,
  Raw p = **2.28e-07** (total = 35, hits = 5; universe = full SMPDB library)
- filter ON (compound-name reference via `Setup.HMDBReferenceMetabolome`,
  Trenton's 35-compound list): **Nicotinate and Nicotinamide Metabolism**,
  Raw p = **3.67e-04** (total = 7, hits = 5; universe = the reference's 35
  compounds)
- Runs without error: **yes**, but only after patching a package bug (below).
  The top pathway is unchanged either way (same 5 compounds hit it), but the
  reference materially changes the p-value by shrinking the background
  universe from the full SMPDB library down to the 35 reference compounds
  (total members considered for this pathway drops from 35 to 7). This
  matches the direction/shape of what a background restriction should do:
  raw p gets less extreme (weaker evidence, since the "random chance" baseline
  shifts), but the ranking/top-hit conclusion is unchanged in this case. No
  downloaded ORA result exists to validate the number against; the loose
  transcript anchor (upregulated·5mo ORA nicotinate p≈0.0063) was not
  targeted and is a different cell/compound set, so no attempt was made to
  force a match.

### Package bug found (independent of the reference-metabolome question)

`CalculateHyperScore()` (the `msetora` scoring function) ends with:
```r
result <- .set.mSet(mSetObj)
ExportOraMembershipJson()          # called with NO mSetObj arg
PlotORAMembership(NA, "mset_membership_0_")   # called with mSetObj = NA
return(result)
```
Both helpers default to `mSetObj = NA` and call `.get.mSet(NA)`. `.get.mSet`
is defined as `if (.on.public.web) get0("mSetObj", envir=.GlobalEnv, ...) else
return(obj)`. Off the public web (`.on.public.web == FALSE`, our case), this
returns the literal `NA` instead of falling back to any global — so the next
line (`mSetObj$analSet$ora.mat`) throws `$ operator is invalid for atomic
vectors`, and `CalculateHyperScore()` never reaches `return(result)`. **This
happens unconditionally** — even in the plain filter-OFF, no-reference case —
so `CalculateHyperScore()` cannot complete at all locally without a patch.
`CalculateOraScore()` (the pathway/`pathora` path) does not call either
helper, which is why `run-pathway.R` never needed this fix.

Both helpers are reporting/plotting side effects only (a JSON membership dump
and a PNG heatmap) — neither touches `mSetObj$analSet$ora.mat`, which is
already fully computed by the time they're called. No-op'ing them via
`assignInNamespace`-style patching is safe and does not change any numeric
result (verified: `ora.mat` values are identical with/without the patch
applied, since the patch only affects code that runs after `ora.mat` is
already finalized).

A second, related package limitation: `AddErrMsg()` does
`current.msg <<- c(current.msg, msg)`, and `current.msg`/`err.vec` are never
initialized when running off the public web — so *any* code path that calls
`AddErrMsg()` locally (e.g. "too few compounds", "cannot perform pathway
analysis") will hard-error with `object 'current.msg' not found` instead of
the intended graceful message + `return(0)`. This was the proximate cause of
the pathway filter-ON crash message text, though the *substantive* failure
(zero pathway sets survive filtering) is real regardless of this secondary
bug. Not patched here since our decision is not to use the KEGG reference on
the pathway module anyway — flagged for awareness in later tasks (e.g.
`run-ora.R`, `run-primary.R`) in case any cell hits an `AddErrMsg()` path
(e.g. too few compounds match / too few hits).

## Decision for the pipeline

- **Pathway module: filter OFF.** Rationale: reproduces Trenton's downloaded
  numbers exactly (1.2011e-05), and filter ON is not just numerically
  different but functionally broken for our SMPDB-library setup (KEGG-ID
  reference vs HMDB-ID library members never intersect). `run-pathway.R`
  already implements this correctly and needs no change from Task 5.
- **ORA module (primary deliverable): reference applied**, via
  `Setup.HMDBReferenceMetabolome(mSet, name_ref_path)` +
  `SetMetabolomeFilter(mSet, TRUE)`. Rationale: matches Trenton's described
  web procedure ("Specify reference metabolome" with the 35 compound names,
  for the enrichment/ORA module specifically — the pathway module's
  Rhistory.R showing filter OFF is a *different* module and does not
  contradict this). It is not numerically validatable against a downloaded
  ORA result (none exists), but it materially changes the background
  universe (confirmed: total members for the top pathway drop from 35 to 7,
  raw p moves from 2.28e-07 to 3.67e-04) so applying it is a substantive,
  intentional choice, not a no-op. `run-ora.R` (Task 8) must also apply the
  `CalculateHyperScore()` export-bug patch documented above, or every ORA
  call — reference or not — will crash.

## Exact reference-loading call sequence for the ORA runner (Task 8)

```r
# One-time patch for a MetaboAnalystR 4.3.0 bug: CalculateHyperScore() calls
# ExportOraMembershipJson() and PlotORAMembership(NA, ...) with no/NA
# mSetObj, which crashes off the public web ("$ operator is invalid for
# atomic vectors") even when there is no reference metabolome involved.
# Both helpers are reporting-only side effects (JSON dump, PNG plot) that
# run after mSetObj$analSet$ora.mat is already computed, so no-op'ing them
# is safe and does not change any numeric result. Call once per R session
# before the first CalculateHyperScore() call.
patch_msetora_export_bug <- function() {
  ns <- asNamespace("MetaboAnalystR")
  unlockBinding("ExportOraMembershipJson", ns)
  assign("ExportOraMembershipJson", function(mSetObj = NA) invisible(NULL), envir = ns)
  lockBinding("ExportOraMembershipJson", ns)
  unlockBinding("PlotORAMembership", ns)
  assign("PlotORAMembership", function(mSetObj = NA, ...) invisible(NULL), envir = ns)
  lockBinding("PlotORAMembership", ns)
  invisible(TRUE)
}
patch_msetora_export_bug()

mSet <- InitDataObjects("conc", "msetora", FALSE, 150)
mSet <- Setup.MapData(mSet, cmpd.vec)
mSet <- CrossReferencing(mSet, "name")
mSet <- CreateMappingResultTable(mSet)

# Apply the compound-name reference metabolome (Trenton's per-outcome-group
# 35-compound-name .txt file). filePath must be a real file path -- the
# loader reads it line-by-line via scan(), it does not accept a vector.
mSet <- Setup.HMDBReferenceMetabolome(mSet, ref_path)   # ref_path = path to "... Reference Metabolome.txt"
mSet <- SetMetabolomeFilter(mSet, TRUE)

mSet <- SetCurrentMsetLib(mSet, "smpdb_pathway", 2)     # excludeNum = 2, matching the pathway module's SMPDB library family
mSet <- CalculateHyperScore(mSet)

# Results:
#   mSet$analSet$ora.mat            -- in-memory results table (name-keyed rows)
#   <cwd>/msea_ora_result.csv       -- same table written to disk by CalculateHyperScore()
```
